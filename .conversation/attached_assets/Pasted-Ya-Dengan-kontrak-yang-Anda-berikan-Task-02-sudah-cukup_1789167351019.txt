# NEXUS-FM — TASK #02

## Authorization & Permission Matrix v1.0

**Status:** READY FOR IMPLEMENTATION
**Dependency:** Task #01 — Foundation & Authentication v1.0 **LOCKED**
**Integration mode:** Additive → Isolated → Verify → Reconcile → Lock

### 1. Objective

Task #02 membangun **authorization engine** di atas fondasi authentication Task #01.

Tujuan utamanya:

> Sistem harus dapat menentukan secara konsisten **siapa boleh melakukan apa, terhadap objek apa, dalam organisasi/scope apa, dan dalam kondisi apa**.

Task #02 **tidak mengubah mekanisme authentication, session, organization, atau baseline schema Task #01**.

# 2. Authorization Model

Model canonical:

```text
USER
 ↓
ROLE
 ↓
PERMISSION
 ↓
RESOURCE
 ↓
ACTION
 ↓
OBJECT
 ↓
SCOPE
 ↓
DECISION
```

Contoh:

```text
TECHNICIAN
    ↓
WORK_ORDER.UPDATE
    ↓
Work Order #WO-001
    ↓
Assigned Work Order
    ↓
ALLOW
```

Sedangkan:

```text
TECHNICIAN
    ↓
WORK_ORDER.UPDATE
    ↓
Work Order milik Facility lain
    ↓
DENY
```

# 5. Critical Rule — PLATFORM_ADMIN

Ini harus dikunci.

```text
PLATFORM_ADMIN ≠ SUPER USER OPERASIONAL
```

`PLATFORM_ADMIN` tidak otomatis memperoleh:

```text
WORK_ORDER.EXECUTE
WORK_ORDER.VERIFY
WORK_ORDER.CLOSE
ASSET.UPDATE
FACILITY.UPDATE
PROJECT.APPROVE
```

Platform administration dan operational authority adalah dua hal berbeda.

Ini mencegah privilege escalation tersembunyi.

# 6. Scope Model

Permission saja tidak cukup.

Evaluator harus mempertimbangkan:

```text
Permission + Object + Scope
```

Canonical scope:

### ORGANIZATION

Semua objek dalam organization yang sama.

```text
ORG_SCOPE
```

### FACILITY

Objek yang berada pada facility yang diizinkan.

```text
FACILITY_SCOPE
```

### BUILDING

Objek dalam building yang diizinkan.

```text
BUILDING_SCOPE
```

### SPACE

Objek dalam space/area tertentu.

```text
SPACE_SCOPE
```

### ASSET

Asset tertentu atau hierarchy asset tertentu.

```text
ASSET_SCOPE
```

### ASSIGNED

Hanya objek yang ditugaskan kepada user.

```text
ASSIGNED_SCOPE
```

### TEAM

Objek yang menjadi tanggung jawab team.

```text
TEAM_SCOPE
```

### VENDOR_ASSIGNMENT

Hanya pekerjaan yang secara eksplisit diberikan kepada vendor.

```text
VENDOR_ASSIGNMENT_SCOPE
```

### OWN

Objek yang dibuat/dimiliki oleh user.

```text
OWN_SCOPE
```

# 7. Scope Inheritance

Inheritance harus dilakukan **server-side**.

Contoh:

```text
Facility
 └── Building
      └── Floor
           └── Space
                └── Asset
                     └── Work Order
```

Jika user memiliki:

```text
FACILITY_SCOPE
Facility A
```

maka evaluator dapat memberikan akses terhadap child object:

```text
Building A
Space A
Asset A
Work Order A
```

**hanya jika hubungan tersebut benar-benar terverifikasi di database.**

Tidak boleh:

```text
objectId cocok
→ langsung ALLOW
```

Harus:

```text
object
→ parent relation
→ facility
→ organization
→ scope validation
→ permission
→ decision
```

---

# 8. Deny by Default

Ini merupakan security invariant.

Jika evaluator tidak menemukan kombinasi:

```text
ROLE
+
PERMISSION
+
VALID SCOPE
```

maka:

```text
DENY
```

Bukan:

```text
ALLOW
```

Tidak boleh ada fallback:

```text
if permission missing
   allow()
```

---

# 9. Precedence Rule

Urutan evaluasi harus konsisten:

```text
1. Authentication
2. Organization isolation
3. Role binding
4. Permission
5. Object existence
6. Object ownership/scope
7. Explicit deny
8. Explicit allow
9. Final decision
```

Recommended final rule:

```text
Explicit DENY
    >
Explicit ALLOW
    >
Inherited ALLOW
    >
No Rule = DENY
```

Namun untuk v1.0, **jangan membuat permission policy terlalu kompleks**.

Prioritasnya adalah deterministic behavior.

# 10. Central Authorization Evaluator

Authorization tidak boleh tersebar di masing-masing route.

Gunakan satu service konseptual:

```ts
authorize({
  userId,
  organizationId,
  resource,
  action,
  resourceId,
  context
})
```

Output:

```ts
{
  allowed: boolean,
  reasonCode: string,
  permission?: string,
  scope?: string
}
```

Contoh:

```json
{
  "allowed": true,
  "reasonCode": "PERMISSION_GRANTED",
  "permission": "WORK_ORDER.UPDATE",
  "scope": "ASSIGNED"
}
```

Contoh deny:

```json
{
  "allowed": false,
  "reasonCode": "SCOPE_DENIED",
  "permission": "WORK_ORDER.UPDATE",
  "scope": "ASSIGNED"
}
```

# 14. Separation of Duties

Beberapa action tidak boleh otomatis diberikan kepada role yang sama.

Terutama:

```text
EXECUTE
VERIFY
CLOSE
```

Contoh:

```text
Technician
    → EXECUTE ✓
    → VERIFY ✕
    → CLOSE ✕
```

Supervisor:

```text
Supervisor
    → EXECUTE ✓
    → VERIFY ✓
    → CLOSE ✓
```

Namun nanti dapat ditambah policy:

```text
executor != verifier
```

sebagai kontrol tambahan pada Task domain terkait.

Task #02 cukup menyediakan **authorization capability**, bukan seluruh business workflow.

# 16. HTTP Behavior

### 401

User belum authenticated:

```http
401 Unauthorized
```

### 403

Authenticated tetapi tidak memiliki authorization:

```http
403 Forbidden
```

### 404

Resource memang tidak ada.

Untuk resource yang ada tetapi berada di organization/scope yang tidak boleh diketahui, implementasi dapat menggunakan `404` untuk mencegah resource enumeration.

Yang penting:

> **Tidak boleh ada cross-organization data leakage.**

```text

user
organization
role
resource
action
resource_id
decision
reason_code

```

Audit harus append-oriented.

Jangan membuat mekanisme yang memungkinkan user biasa menghapus histori authorization.

# 18. Security Invariants

Task #02 dianggap gagal jika salah satu berikut terjadi:

### Cross organization

```text
User Organization A
→ Resource Organization B
→ ALLOW
```

**FAIL**

### Missing permission

```text
Role
→ permission tidak ada
→ ALLOW
```

**FAIL**

### Missing scope

```text
Permission ada
→ object di luar scope
→ ALLOW
```

**FAIL**

### UI bypass

```text
button disembunyikan
tetapi API langsung dipanggil
→ ALLOW
```

**FAIL**

### Platform admin escalation

```text
PLATFORM_ADMIN
→ otomatis operational superuser
```

**FAIL**

### Direct object access

```text
GET /api/work-orders/:id
```

tidak boleh menjadi bypass terhadap scope.

# 19. Test Matrix

Minimal test suite:

### Authentication

```text
Unauthenticated → 401
Authenticated → continue authorization
```

### Organization

```text
Same organization → eligible
Different organization → DENY
```

### Role

```text
Role assigned → evaluate
Role absent → DENY
```

### Permission

```text
Permission exists → continue
Permission absent → DENY
```

### Scope

```text
Within scope → ALLOW
Outside scope → DENY
```

### Assignment

```text
Assigned technician → ALLOW
Unassigned technician → DENY
```

### Vendor

```text
Vendor assigned WO → ALLOW
Vendor unrelated WO → DENY
```

### Tenant

```text
Tenant own request → ALLOW
Tenant other tenant request → DENY
```

### Admin

```text
Platform admin
→ platform administration → ALLOW
→ operational action without permission → DENY
```

### API bypass

Semua test harus dilakukan **langsung terhadap API**, bukan hanya melalui UI.
